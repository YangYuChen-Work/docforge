# 场景1文档生成 POC 实施路线

## 1. 总体原则

- 先完成真实闭环，再扩展漂亮的页面。
- 先支持 DOCX/XLSX 和 DOCX 输出，再扩展 PDF、图片和复杂格式。
- 先用 SQLite 和本地文件，再考虑迁移到 PostgreSQL 或对象存储。
- 先用 Mock AI 验证流程，再接入真实 AI。
- 每完成一个阶段，都必须有可运行结果和验收数据。

## 2. 阶段划分

### 阶段0：项目骨架和文档基线

目标：建立真实项目目录和运行方式。

工作项：

- 初始化 Python 虚拟环境或项目依赖。
- 创建 FastAPI 入口。
- 创建 SQLite 连接和基础迁移。
- 创建本地存储目录。
- 将 `DOC_PROJECTS`、`DOC_TEMPLATES` 转换为种子数据。
- 保留 `reference/demo-platform` 作为布局和参考数据，不直接作为生产 API 数据源。
- 增加健康检查接口。

验收：

- 本地可以启动后端。
- `GET /health` 返回成功。
- 数据库文件可以创建。
- P001-P005 可以从数据库查询。

### 阶段1：真实文件导入和解析

目标：让场景1资料包成为系统中的真实资料。

工作项：

- 导入 `assets/scenario1/sources/` 中的 DOCX 和 XLSX。
- 设计 SourceDocument 和 ParsedSourceContent 表。
- 实现 DOCX 标题、段落和表格解析。
- 实现 XLSX 工作表、表头和单元格解析。
- 保存原始文件哈希。
- 保存解析结果 JSON。
- 提供资料列表和解析状态页面。

验收：

- 10 个 DOCX 和 2 个 XLSX 都能显示导入结果。
- 每个文件都有解析状态。
- 至少能查看一个 Word 表格和一个 Excel 工作表的结构化内容。
- 解析失败不影响其他文件。

### 阶段2：真实模板和章节配置

目标：让系统理解目标文档的章节和模板结构。

工作项：

- 导入 `XX产品开发立项暨设计和开发输入报告.docx` 作为目标模板参考。
- 解析模板标题、章节和表格。
- 建立模板章节配置。
- 为每个章节配置资料类型和关键词。
- 标记服务可行性资料缺失。
- 支持模板预览和章节资料需求查看。

验收：

- 页面能展示目标模板的主要章节。
- 用户能看到每个章节需要哪些来源资料。
- 资料映射结果有已匹配、部分匹配、未匹配和冲突状态。

### 阶段3：Mock AI 章节生成

目标：在没有真实模型密钥时，也能验证生成业务闭环。

工作项：

- 定义 ChapterGenerationRequest 和 ChapterGenerationResult。
- 实现 MockAIProvider。
- Mock 返回固定且可测试的章节、引用和待补充项。
- 实现生成任务状态机。
- 保存章节正文、引用、缺失项和冲突。
- 支持单章节重试。

验收：

- P001 可以创建场景1生成任务。
- 生成任务能从 created 走到 awaiting_confirmation。
- 至少 3 个章节有引用。
- 缺少服务可行性资料的章节有待补充提示。

### 阶段4：真实 AI Provider

目标：将 Mock 生成替换为可配置的真实模型生成。

工作项：

- 实现 DeepSeek V4 Pro Provider；如果服务接口兼容 OpenAI-compatible 协议，复用通用客户端适配。
- 所有密钥只从环境变量读取。
- 提供 `.env.example`，真实 `.env` 不提交到 Git。
- 设计章节生成提示词模板。
- 将来源片段、表格数据和项目数据按章节注入上下文。
- 对模型返回做 JSON Schema 校验。
- 处理超时、限流、格式错误和模型不可用。
- 保存 AI 调用记录和模型信息。

验收：

- 可以在不改代码的情况下切换 Mock/真实 Provider。
- AI 生成结果能保存引用和待补充项。
- 模型返回非法结构时不会污染文档数据。
- 没有来源依据的内容会被标记为待补充或低置信度。

### 阶段5：章节查看、人工修改和版本

目标：让生成文档具备可确认和可追溯能力。

工作项：

- 实现三栏文档编辑页。
- 左侧显示章节树和状态。
- 中间显示章节正文和表格。
- 右侧显示引用、缺失项、冲突和生成建议。
- 支持人工编辑章节。
- 支持章节确认和单章节重新生成。
- 创建 DocumentVersion。
- 创建 AuditLog。

验收：

- 人工修改后能保存。
- 重新生成不会覆盖旧版本。
- 可以查看章节引用。
- 可以查看是谁、什么时候执行了什么操作。

### 阶段6：真实 DOCX 输出

目标：把已确认的内容写回目标 Word 模板，生成可打开的正式文档。

工作项：

- 复制模板到生成目录。
- 根据章节定位写入正文。
- 写入或更新目标表格。
- 保留模板样式和基本结构。
- 将待补充项以明确标记写入或保留在生成报告中。
- 记录导出文件路径和版本。

验收：

- 生成 DOCX 可以打开。
- 原始模板没有被修改。
- 输出文档包含已确认章节。
- 输出文档保留待补充项提示或导出检查报告。

### 阶段7：POC 收口

目标：完成本地可重复运行、可演示、可继续开发的 POC。

工作项：

- 编写一键启动脚本。
- 编写场景1数据导入脚本。
- 编写端到端验收脚本。
- 完善错误提示和日志。
- 将前端改为克制的工程管理视觉。
- 更新 README 和 Claude Code 指南。

验收：

- 新环境可以按文档启动。
- 一条命令可以导入场景1资料。
- 一条业务链路可以生成 DOCX。
- 失败原因可定位。
- 文档和代码范围一致。

## 3. 后续方向

POC 完成后再评估：

1. 测试用例生成真实后端。
2. 规则库和规则审核。
3. 产品模块智能选配和 BOM 维护。
4. PDF、图片和架构图解析。
5. 向量检索和历史案例库。
6. 多用户、权限和审批流。

这些方向不得提前侵入场景1 POC 的核心实现。

## 4. Claude Code 执行要求

每次开发任务必须说明：

- 要解决的业务问题。
- 影响的领域对象。
- 修改的文件。
- API 或数据结构变化。
- 验收命令。
- 失败场景。

每完成一个阶段，必须运行：

- 后端测试。
- 解析样例测试。
- 场景1端到端测试或当前阶段可执行的最小替代测试。
- 生成文件可打开性检查。

如果发现需求不明确，优先回到 `CONTEXT.md`、`PRD.md` 和 `BUSINESS_DOMAIN.md`，不要自行扩大范围。
