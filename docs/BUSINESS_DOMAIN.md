# 场景1文档生成业务与领域说明

## 1. 业务背景

产品研发过程中会产生大量专业资料：市场调研、技术调研、质量调研、技术可行性、制造可行性、采购可行性、标准化要求、盈利分析和项目计划等。最终项目文档通常需要把这些资料重新组织成统一格式的正式报告。

当前业务的主要痛点：

1. 资料分散在不同文件和专业团队中。
2. 同一事实在多个文件中重复维护，容易产生不一致。
3. 文档章节结构和格式需要人工套用模板。
4. 生成内容缺少清晰的来源追溯。
5. 缺失资料通常在文档定稿阶段才被发现。
6. 反复复制、整理和润色占用工程师大量时间。

系统要解决的不是“自动写一篇漂亮文章”，而是：

> 将项目资料按标准模板组织成可追溯、可确认、可继续编辑的研发文档初稿。

## 2. 业务边界

### 2.1 输入边界

当前场景1输入包括：

- 一个研发项目。
- 一个目标 Word 模板。
- 多份 Word 来源资料。
- 多份 Excel 来源资料。
- 可选的历史项目文档。
- 可选的用户补充说明。

### 2.2 输出边界

输出包括：

- 按模板组织的项目文档。
- 章节级生成内容。
- 来源引用记录。
- 待补充资料清单。
- 内容冲突清单。
- 文档版本。
- 可下载的 DOCX 文件。

### 2.3 当前不负责的事情

- 系统替代专业工程师做最终技术判断。
- 系统自动决定产品方案或研发立项结论。
- 系统为缺少依据的指标生成“看起来合理”的数字。
- 系统自动完成企业审批和签名。
- 系统直接改写原始来源文件。

## 3. 业务角色

### 产品/项目负责人

负责选择项目和模板、发起生成任务、处理缺失资料、确认最终内容。

### 专业工程师

负责维护专业来源资料，核对 AI 生成内容，补充专业判断和技术数据。

### 文档管理员

负责维护模板结构、模板章节说明、格式要求和资料匹配规则。

### 评审人员

负责检查文档的完整性、准确性、来源和风险项，并留下评审意见。

POC 中不实现复杂账号体系，但页面和数据模型要保留角色语义。

## 4. 核心业务流程

### 4.1 项目选择

用户从项目列表中选择项目。项目数据初始来自 `reference/demo-platform/doc-data.js` 的 `DOC_PROJECTS`。

项目阶段会影响模板推荐：

| 项目阶段 | 可能使用的模板 |
|---|---|
| 前期调研 | 市场需求分析报告、技术调研报告 |
| 方案设计 | 总体设计方案、技术可行性分析报告 |
| 需求冻结 | 产品设计任务书 |
| 详细设计 | 结构设计说明书、液压系统设计说明书 |
| 试制验证 | 试制验证方案 |
| 评审归档 | 设计评审材料 |

### 4.2 模板选择

模板决定：

- 文档用途。
- 章节层级。
- 每章需要的资料类型。
- 是否包含表格、图片或计算结果。
- 生成语气和内容要求。
- 导出格式和版式。

用户可以接受系统推荐，也可以手动选择其他启用模板。

### 4.3 资料准备

资料准备分为三个阶段：

1. 上传：保存原始文件并记录文件信息。
2. 解析：提取段落、标题、表格和可识别的元数据。
3. 关联：将资料关联到项目和生成任务。

资料解析成功不代表资料足以支撑生成。系统还需要进行章节级匹配。

### 4.4 章节匹配

章节匹配是生成前的关键检查。

匹配状态：

- 已匹配：资料类型和内容都能支撑章节。
- 部分匹配：有资料，但缺少关键字段或关键表格。
- 未匹配：未找到相关资料。
- 冲突：多个来源对同一事项表达不一致。

匹配状态必须对用户可见，并允许用户手动添加或移除资料。

### 4.5 AI 生成

AI 生成以章节为单位，不建议一次把全部资料和模板拼成长文本发送给模型。

每章生成时，系统提供：

- 当前章节标题和写作要求。
- 模板结构。
- 已匹配的来源片段。
- 项目基本信息。
- 用户补充说明。
- 已知冲突和缺失项。

AI 返回：

- 正文。
- 表格建议或表格数据。
- 引用列表。
- 待补充项。
- 冲突说明。
- 生成置信度或质量提示。

### 4.6 人工确认

AI 生成内容只能是草稿。用户可以：

- 接受章节。
- 修改正文。
- 修改表格。
- 添加补充说明。
- 重新生成章节。
- 标记资料缺失。
- 标记来源冲突。
- 添加人工评审意见。

只有用户确认后的章节，才能进入最终文档导出状态。

### 4.7 导出和归档

导出时系统将：

1. 读取模板原始结构。
2. 将已确认章节内容写入目标位置。
3. 保留模板中的基础样式和表格。
4. 生成新的 DOCX 文件。
5. 记录导出版本和文件路径。

原始模板和来源资料永远不被覆盖。

## 5. 业务状态机

### 5.1 来源资料状态

```text
uploaded → parsing → parsed
                    ↘ parse_failed → retrying → parsing
```

状态说明：

- `uploaded`：文件已保存，尚未解析。
- `parsing`：正在提取内容。
- `parsed`：已形成可供匹配的结构化内容。
- `parse_failed`：解析失败，需要查看错误或重新解析。

### 5.2 生成任务状态

```text
created → preparing → generating → awaiting_confirmation → completed
              ↘ failed
```

状态说明：

- `created`：用户刚创建任务。
- `preparing`：检查模板、解析资料、建立章节匹配。
- `generating`：正在生成章节。
- `awaiting_confirmation`：初稿已生成，等待人工确认。
- `completed`：章节和导出结果已确认。
- `failed`：任务无法继续，需要处理错误。

### 5.3 文档状态

```text
draft → generating → editing → reviewing → archived
                         ↘ failed
```

### 5.4 章节状态

```text
pending → generating → generated → confirmed
              ↘ failed       ↘ needs_material
```

## 6. 业务规则

### 规则 BR-001：项目与文档分离

一个项目可以拥有多个文档，一个文档只能归属于一个项目。

### 规则 BR-002：模板决定文档结构

文档生成不能脱离模板章节结构。AI 可以生成章节内容，但不能无授权地删除或改变模板的核心章节。

### 规则 BR-003：资料不足必须显式化

没有来源依据的字段必须标记为待补充，不允许默认填充为事实。

### 规则 BR-004：来源可追溯

由 AI 生成的事实性内容至少记录来源文件；能定位到章节、表格或单元格时必须继续记录更细定位。

### 规则 BR-005：冲突不静默覆盖

多个来源对同一事实有不同内容时，系统必须展示冲突并交给用户确认。

### 规则 BR-006：重新生成不覆盖历史

重新生成章节必须保存旧版本内容、旧引用和生成时间。

### 规则 BR-007：源文件只读

源文件是证据，不是编辑对象。系统生成的规范化内容必须写入独立文档或版本。

### 规则 BR-008：导出前检查

导出前至少检查：

- 是否有章节生成失败。
- 是否存在未处理的冲突。
- 是否存在待补充项。
- 是否有章节未确认。
- 模板文件是否可读。

POC 可以允许用户选择“带待补充项导出”，但必须在导出记录中标记。

## 7. 场景1资料与业务含义

场景1来源资料不是随机附件，而是产品开发立项和设计输入的不同专业输入：

| 资料 | 业务含义 |
|---|---|
| 市场调研报告 | 市场规模、客户群、工况、痛点和开发建议 |
| 技术调研报告 | 市场/工况/竞品的技术视角分析 |
| 产品营销策略报告 | 市场定位、销售策略、目标客户、价格和风险 |
| 质量调研报告 | 竞品或历史产品的质量问题、原因和改进建议 |
| 产品质量目标 | 新产品需要达到的质量指标和指标定义 |
| 技术可行性分析报告 | 技术路线、关键参数、技术难题、成本和风险 |
| 标准化综合要求 | 法律法规、国家标准、行业标准和执行要求 |
| 制造可行性分析报告 | 工序、工艺、设备、制造困难点和解决措施 |
| 采购可行性分析报告 | 关键物料、供应资源、采购成本、交期和供应商风险 |
| 盈利分析报告 | 售价、成本、毛利、销量和产品经济效益 |
| XVPM-WBS里程碑.xlsx | 项目计划和里程碑信息 |
| XVPM-项目预算-假数字.xlsx | 项目预算或成本相关输入 |

最终的《产品开发立项暨设计和开发输入报告》是这些资料的综合汇总，不是单一来源文档的复制。

## 8. 领域边界和常见误解

### “项目”不等于“项目文档”

项目是业务容器；总体方案、设计任务书、验证方案都是项目下的不同文档。

### “模板”不等于“资料”

模板规定写什么、怎么排版；资料提供写作依据。

### “生成成功”不等于“业务确认”

AI 生成完成只代表形成草稿，不代表技术内容已经正确。

### “引用”不等于“复制原文”

引用要表达来源关系，可使用摘要或结构化定位，不要求把整份源文件复制到正文。

### “待补充”不等于“生成失败”

资料缺失可以生成部分文档，但必须把缺失信息清晰呈现。
